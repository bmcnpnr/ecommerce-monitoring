# Ecommerce Monitoring

Observability stack for the ecommerce microservices platform.

The full guide covers what each service emits, every scrape job, alert and
dashboard, how to query logs and traces, and the known gaps. It is at
[docs/observability.md](https://github.com/bmcnpnr/ecommerce-platform/blob/develop/docs/observability.md)
in ecommerce-platform (`../ecommerce-platform/docs/observability.md` when the
repositories are checked out side by side).

## Quick Start

The monitoring stack is embedded in the main ecommerce-platform docker-compose. Run the full stack from `ecommerce-platform/`:

```bash
cd ecommerce-platform
docker compose up --build
```

Or start only the monitoring services:

```bash
docker compose up prometheus grafana loki promtail tempo alertmanager \
  node-exporter cadvisor kafka-exporter blackbox-exporter nginx-exporter \
  postgres-exporter-userdb postgres-exporter-productdb postgres-exporter-orderdb \
  postgres-exporter-paymentdb postgres-exporter-shippingdb postgres-exporter-reviewdb \
  mongodb-exporter-catalogdb
```

## What is Instrumented

### Spring Boot Services (all 10)
- `/actuator/prometheus` — Prometheus scrape endpoint
- JVM metrics (heap, GC, threads, classes)
- HTTP request metrics with SLO histograms (50ms/100ms/200ms/500ms/1s/2s)
- HikariCP connection pool metrics (`hikaricp_*`) in the six services with a Postgres database
- Resilience4j circuit breaker metrics (`resilience4j_circuitbreaker_*`): catalog-, order- and review-service (breaker `product-service`) and payment-service (breaker `order-service`)
- Dead letters per source topic (`kafka_dlt_published_total`, `kafka_dlt_dropped_total`) in order-, shipping- and notification-service, registered at the first dead letter; expired carts (`orders_reservations_expired_total`) in order-service
- `logback_events_total{level}`: log events per level, the basis of the log-volume and error-log alerts
- Transactional outbox gauges and counters (`outbox_events_pending`, `outbox_events_parked`, `outbox_events_published_total`, `outbox_publish_failures_total`) in order-, payment- and shipping-service
- OTLP traces sent to Tempo on port 4318. Gateway → service hops are linked; Feign calls and Kafka messages are not traced.
- Every service logs one format, `%d{yyyy-MM-dd HH:mm:ss} [%thread] [%X{correlationId:-}] [%X{traceId:-}] %-5level %logger{36} - %msg%n` (the brackets are empty outside a request); Promtail parses exactly this

### Infrastructure
- **cAdvisor** — CPU, memory, network, disk I/O per container
- **Node Exporter** — CPU, memory, disk and network of the Docker engine VM (on Docker Desktop this is the Linux VM, not the Windows/macOS host)
- **Kafka Exporter** — Broker count, consumer group lag, topic offsets
- **Kafka UI** — Web UI for browsing topics, viewing messages, and inspecting consumer groups (http://localhost:8090)
- **Postgres Exporters** — One per Postgres database (userdb, productdb, orderdb, paymentdb, shippingdb, reviewdb)
- **MongoDB Exporter** — percona/mongodb_exporter for catalogdb, the MongoDB behind catalog-service (`mongodb_up`, connections, opcounters, dbstats)
- **Blackbox Exporter** — HTTP probes for all 10 service health endpoints + frontend
- **Nginx Exporter** — Frontend nginx active connections, request rate

### Logging (Loki + Promtail)
- The ten Spring services, Kafka and the frontend are collected (via the Docker socket under compose, via the Kubernetes API under k8s). Only those containers are discovered: Promtail 3.1 tails a container that a relabel `keep` rule dropped and ships it with no labels, which Loki rejects with HTTP 400, so the allow-list is a discovery filter
- One entry per log event: a stack trace is grouped with the line that started it (multiline stage, at most 128 lines); Kafka's own format is grouped too
- `level` is the only stream label (six possible values). `correlationId`, `traceId` and `thread` are structured metadata, never labels, and are omitted when empty
- DEBUG and TRACE are dropped before Loki (they stay in `docker logs`)
- Entries keep the timestamp the container runtime recorded (nanosecond precision), not the pattern's whole second
- Each container is counted by Promtail before anything is dropped (`promtail_custom_log_lines_total`, `promtail_custom_log_bytes_total`) and limited to 300 entries/s; the excess is dropped and counted (`logentry_dropped_lines_by_label_total`)
- Positions are kept on a volume (`promtail-data`), so a recreated Promtail does not re-read every container's whole log
- Searchable in Grafana → Explore → Loki; every log line with a trace links to Tempo

### Disk bounds
Every store has a size or rate bound, so a runaway producer is dropped (and alerted on) instead of filling the Docker VM disk:

| Store | Bound | Where |
|---|---|---|
| Container logs | json-file 50 MB × 3, non-blocking | `x-default-logging` in docker-compose.yml |
| Loki | 512 KB/s for the stack, 128 KB/s per stream (burst 2 MB), 64 KB per entry, 1000 streams; WAL replay capped at 192 MB | `loki/loki-config.yml` |
| Tempo | 1 MB/s ingestion (burst 4 MB), 2 MB per trace, 50000 generated series | `tempo/tempo-config.yml` |
| Prometheus | 5 GB of blocks, 50000 samples per scrape | compose/k8s flags, `prometheus.yml` |
| Kafka | 128 MiB per partition, 32 MiB segments | `KAFKA_LOG_*` in compose and `20-kafka.yaml` |

### Tracing (Tempo)
- All services export OTLP traces to Tempo
- Every log line inside a request carries its trace ID; Loki links it to Tempo, and Tempo links a span to the service's log lines
- Service graph and span metrics auto-generated
- Viewable in Grafana → Explore → Tempo

## Alert Rules

Six rule files:

| File | Alerts |
|---|---|
| `service-alerts.yml` | ServiceDown, ServiceEndpointUnhealthy, HighErrorRate, CriticalErrorRate, HighP99Latency, JvmHeapUsageHigh, JvmHeapUsageCritical, JvmGcPauseHigh, CircuitBreakerOpen |
| `logging-alerts.yml` | ServiceLogRateHigh/Critical, ServiceErrorLogRateHigh/Critical, ContainerLogVolumeHigh/Critical, PromtailDroppingLogs, PromtailDroppedEntries, LokiRateLimitingLogs, LokiRejectingLogs, PromtailNoActiveTargets, TempoDiscardingSpans, MonitoringStackDown |
| `outbox-alerts.yml` | OutboxBacklog, OutboxBacklogGrowing, OutboxBacklogCritical, OutboxEventsParked, OutboxPublishFailing, OutboxRelayStalled |
| `infrastructure-alerts.yml` | ContainerHighCpuUsage, ContainerHighMemoryUsage, ContainerRestarting, HostHighCpuLoad, HostOutOfMemory, HostDiskSpaceLow, HostDiskSpaceCritical, HostDiskWillFillWithin24h, HostDiskWillFillWithin4h, PrometheusTsdbNearSizeLimit, PrometheusSampleLimitExceeded, ExporterDown |
| `database-alerts.yml` | PostgresDown, PostgresTooManyConnections, PostgresDeadlocks, PostgresSlowQueries, DatabasePoolTimeouts, DatabasePoolSaturated, MongoDown, MongoTooManyConnections |
| `kafka-alerts.yml` | KafkaBrokerDown, KafkaConsumerGroupLag, KafkaConsumerGroupLagCritical, KafkaUnderReplicatedPartitions, KafkaPartitionHasNoLeader, KafkaConsumerGroupNoMembers, KafkaConsumerStuck, KafkaDeadLetterRecords, KafkaDeadLetterFlood, KafkaDeadLetterDropped |

> The `Host*` alerts read node-exporter, which measures the Docker engine VM.
> On Docker Desktop they describe that VM, not the Windows/macOS host. The disk
> alerts select real filesystems by type (not `mountpoint="/"`) and fold the
> mountpoints of one device into one alert.

The rules have unit tests in `prometheus/tests/` (`promtool test rules`): every
new or fixed rule has a case that makes it fire and one that must stay quiet. CI
runs them with the config checks (`.circleci/validate.Dockerfile`); locally:

```bash
docker build --target prometheus-validation --file .circleci/validate.Dockerfile .
```

Rules that could not fire, or not reliably, were rewritten: `PostgresDeadlocks`
(`rate()` with `for: 5m` never reported a single deadlock), `KafkaPartitionHasNoLeader`
(kafka-exporter emits no sample for a leaderless partition, never `-1`),
`HostDiskSpaceLow` and `HostDiskSpaceCritical` (they selected `mountpoint="/"`,
which may not be the disk Docker's data lives on) and `CircuitBreakerOpen` (it watched
`state="open"` alone, so each half-open trial call of a breaker that stays broken
reset its clock; it now counts open, half-open and forced-open together for 3 minutes).

## Configuration

Run `ecommerce-platform/init-secrets.sh` first: it creates `ecommerce-platform/.env` (where `docker compose` reads it from) with generated secrets. To change the non-secret settings in this directory's `.env.example`, append them to that file.

Key variables:
- `GRAFANA_ADMIN_PASSWORD` — change before deploying anywhere non-local
- `TRACING_SAMPLING_PROBABILITY` — set to `0.1` (10%) for high-traffic environments
- `JWT_SECRET` — must match across all services

## Alerting

Edit `alertmanager/alertmanager.yml` to configure a real notification channel:
- **Slack**: uncomment the `slack_configs` section and set `SLACK_WEBHOOK_URL`
- **Email**: set `smtp_*` globals and configure SMTP receiver
- **PagerDuty**: use `pagerduty_configs`
